## Deploy / Operação
- [x] Fluxo completo `scripts/deploy.sh production` **validado localmente** (ambiente Docker da máquina): criados containers `mongodb-prod`/`redis-prod` na rede `auth-network` e `.env.prod` apontando para eles (mongo local `auth_prod`, redis db 1). O deploy rodou de ponta a ponta N vezes: testes → backup → build multi-stage → compose prod → healthcheck → smoke tests. **Prova de funcionamento**: `/health` = healthy (mongo+redis `connected`), `/metrics` 401 sem token e 200 com `x-metrics-token`, fluxo HTTP completo register → login → profile → refresh (rotação, reuso 401) → logout (access revogado 401, blacklist `token_blacklist:*` no Redis). ⚠️ 🔥 **3 bugs REAIS encontrados e corrigidos**: (1) `prepare: husky` quebrava `npm ci --omit=dev` no Dockerfile → `husky || true`; (2) `trap ERR` NÃO dispara com `set -e` quando a falha ocorre na última função → **rollback nunca rodava**; refatorado para checagem explícita (checagem de retorno em cada etapa + `rollback` chamado em `build_and_push`/`deploy_*`); (3) drift de rede: `docker-compose.prod.yml` divergia do dev (sem `ipam`) → compose tentava recriar a rede e falhava → definições alinhadas (mesmo subnet `172.20.0.0/16`). Rollback **validado ao vivo**: deploy com `/health` errado → falha → `Rollback concluído` restaurando o backup (tag volta ao mesmo image ID do backup, container healthy). Detalhes de staging e push para registry real permanecem dependentes de ambiente externo (registry+host).
- [x] Rollback documentado e **implementado** em `scripts/deploy.sh`: backup automático ANTES do build prod (captura a versão em execução) + `rollback()` restaura a última imagem de backup e sobe o compose de volta. ✅ **Validado ao vivo** no teste acima.
